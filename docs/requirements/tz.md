## 1. Описание и границы проекта

**SkillSwap** — учебная платформа для обмена навыками: пользователь сообщает, чему может научить, выбирает навыки, которым хочет научиться, изучает предложения других пользователей и инициирует обмен. Проект выполняется командой за четыре недели. **[СОЗВОН]**

- Реализация — клиентское SPA. Текущая командная документация определяет стек React, TypeScript, Redux Toolkit; данные — «база» внутри приложения (образцы в JSON + изменения в `localStorage`), без обязательного сервера. **[КОМАНДА]**
- Пользовательские данные и взаимодействия имитируются локально. Полноценное взаимодействие между разными людьми и серверная система рекомендаций не требуются. **[СОЗВОН]**
- Наставник разрешил создание backend как необязательное расширение при согласовании с командой; это не входит в основной объём. **[ОПЦИЯ]**
- Требуется визуальное сходство с Figma, но **pixel-perfect** не обязателен. Требуется десктопная версия; адаптивность под мобильные устройства необязательна и не оценивается как обязательный критерий. **[СОЗВОН]**
- Основой проверки служат обязательные MVP-сценарии и индивидуальный вклад участников через задачи, коммиты и PR. **[СОЗВОН]**

**Ссылки проекта [КОМАНДА]:** [репозиторий](https://github.com/PM-YandexPracticum/SkillSwap_58_4), [доска задач](https://github.com/orgs/PM-YandexPracticum/projects/133/views/1), [макет Figma](https://www.figma.com/design/40gXmyAoxwwnb9kBxI5B8y/SkillSwap-Red.1-), [методология FSD](https://feature-sliced.design/ru/).

## 2. Роли и состояния пользователя

- **Гость:** просматривает главную, карточки навыков, статические страницы, использует доступный поиск и фильтры; может перейти к входу и регистрации. Попытка поставить лайк без авторизации должна перенаправлять к регистрации/входу. **[СОЗВОН]** Гость, нажавший лайк или «Предложить обмен», попадает на **вход** и после него возвращается на предыдущую страницу. **[ТЗ-Н]**
- **Авторизованный пользователь:** просматривает и лайкает предложения, открывает избранное, предлагает обмен, получает локальное уведомление о собственном предложении, редактирует профиль, выходит из аккаунта. **[СОЗВОН]**
- **Пользователь при регистрации:** проходит три последовательных шага, создаёт профиль и одно предложение обучать навыку. **[СОЗВОН]**
- Роли разработчиков (тимлид, заместитель, участник) не являются пользовательскими ролями приложения и описаны в разделе организации работы.

## 3. Данные и доменная модель

### 3.1. Пользователь (User)

Набор фактически озвученных полей: уникальный `id`; email/логин; пароль для демонстрационного входа; имя; дата рождения/возраст; пол; город; аватар; список подкатегорий, которым хочет научиться; **одно** собственное предложение о навыке, которому может научить; дата создания; количество лайков; список ID понравившихся пользователей; необязательное описание «О себе», изначально пустое. **[СОЗВОН]**

**Правила:**
- Для демонстрации подготовить ориентировочно **40–50** моковых пользователей, с разными датами регистрации и количеством лайков. **[СОЗВОН]**
- Возможность входа должна существовать под аккаунтами из мокового набора. **[СОЗВОН]**
- Список избранного конкретного пользователя хранит ID тех пользователей, чьи предложения он лайкнул. **[СОЗВОН]**
- Возраст в UI выводится из даты рождения (`getAge`). **[КОМАНДА]**
- Пол может быть «Не указан» — это отдельный вариант в списке на шаге 2. **[МАКЕТ]**
- Для локальных данных не использовать настоящие личные пароли; схема хранения демонстрационных учетных данных должна оставаться исключительно учебной. **[РЕКОМЕНДАЦИЯ ПО БЕЗОПАСНОСТИ]**

### 3.2. Город (City)

Отдельная простая сущность для выбора города пользователя и фильтрации. Наставник упоминает условный массив городов; конкретный обязательный перечень на созвоне не закреплён. **[СОЗВОН]** Справочник ~15 городов: в фильтре видны первые 5 и «Все города», на шаге 2 — список с поиском по вводу. **[МАКЕТ + КОМАНДА]**

### 3.3. Категория и подкатегория (Category / Subcategory)

Категория содержит несколько подкатегорий. Например, «Творчество и искусство» → «Фотография». Структура может быть вложенной либо нормализованной, выбор реализации — за командой. **[СОЗВОН]**

**Связанные селекты:**
1. После выбора категории показываются только входящие в неё подкатегории.
2. Если категория не выбрана, список подкатегорий содержит все возможные варианты.
3. При выборе подкатегории сначала автоматически устанавливается её родительская категория.
4. Несогласованные пары категорий и подкатегорий недопустимы.
5. Логика применяется как на шаге 2, так и на шаге 3 регистрации. **[СОЗВОН]**
6. На шаге 2 оба списка — с чекбоксами (множественный выбор), на шаге 3 — одиночный выбор. **[МАКЕТ]**

### 3.4. Предложение обучения навыку (SkillOffer)

На третьем шаге регистрации пользователь создаёт **одно** предложение: произвольное название навыка, категория, подкатегория, описание и фотографии. Например, «Рисование акварелью» — название; «Творчество и искусство» — категория; «Рисование и иллюстрации» — подкатегория. **[СОЗВОН]**

**Важно:** «Навыки, которым хочу научиться» — список **подкатегорий**, а «Навык, которому могу научить» — одно конкретное предложение с пользовательским названием. Наставник не требовал автоматической смысловой проверки соответствия свободного названия категории. **[СОЗВОН]**

### 3.5. Уведомление (Notification)

Локальная запись факта «вы предложили обмен пользователю X»; статусы «новое» и «просмотренное», возможность перейти к карточке X, отметить все уведомления прочитанными и очистить список. **[ТЗ-Н]** Это **не** сообщение от второго пользователя и **не** настоящий обмен между двумя учетными записями. **[СОЗВОН]**

### 3.6. Сохранение данных

Данные живут внутри приложения за слоем доступа `entities/*/api`: образцы — JSON в `public/db/` (45 пользователей с навыками, справочники; скачиваются через `fetch` при первом обращении), все изменения — регистрация, лайки, профиль, обмены, уведомления — сохраняются в `localStorage` и переживают перезагрузку страницы. Переход на настоящую БД меняет только слой `api`. **[КОМАНДА]**

- Загруженные пользователем фото хранятся как data URL; лимит файла 1 МБ (у `localStorage` ~5 МБ на сайт). **[КОМАНДА]**
- Сессия и тема — отдельные ключи `localStorage`. **[КОМАНДА]**
- По ТЗ наставника справочные JSON (пользователи, навыки, категории, города) лежат в `public/db` — перенесены задачей P4-10; изменился только слой `entities/*/api`. **[ТЗ-Н]**

## 4. Общий каркас интерфейса

- **Header:** логотип, «О проекте», меню «Все навыки», строка поиска «Искать навык» с иконкой лупы, переключение темы как необязательная возможность, вход/регистрация для гостя, аватар и имя для авторизованного пользователя, избранное и колокольчик уведомлений. **[СОЗВОН]**
- **Footer:** «О проекте» переводит на страницу команды; «Все навыки» переводит на отдельную статическую страницу (в отличие от выпадающего меню в Header); контакты, блог, политика конфиденциальности и пользовательское соглашение — заглушки согласно созвону. **[СОЗВОН]**
- Логотип, кнопки, карточки, плашки, аватар и другие повторяющиеся блоки необходимо выделять для повторного использования. **[СОЗВОН]**
- Вёрстка ориентирована на десктопную сетку из трёх колонок карточек. **[СОЗВОН]**

## 5. Главная страница

### 5.1. «Популярное»
- Сортировка предложений по убыванию количества лайков.
- Первоначально показываются **3** карточки.
- Кнопка «Смотреть всё» расширяет секцию до **9** карточек, сдвигая следующие секции ниже; повторное нажатие сворачивает обратно до 3. **[СОЗВОН]**

### 5.2. «Новое»
- Сортировка по дате создания пользователя/карточки (на созвоне явно указана дата создания пользователя).
- Аналогичное расширение 3 → 9 → 3 карточки. **[СОЗВОН]**

### 5.3. «Рекомендуемое»
- Отображение карточек в произвольном (случайном) порядке; персональную рекомендательную систему не делать.
- Карточки могут дублироваться между разными секциями.
- **Бесконечная прокрутка:** догружать следующие карточки при прокрутке, ориентир **по 6** за порцию (два ряда по три); показывать краткий индикатор загрузки. Не выводить все 40–50 карточек сразу. **[СОЗВОН]**

### 5.4. Поиск и фильтрация
- Поиск навыка по введённому запросу; запуск по Enter или нажатию на иконку лупы. При непустом поле — кнопка очистки «×». **[СОЗВОН]** В макете (1:2819) крестика нет — оставляем его по словам наставника. **[РЕШЕНИЕ]**
- Ищем по названию навыка; результат — «Подходящие предложения: N». **[ТЗ-Н]**
- Фильтры: «Хочу научиться» / «Могу научить», категория, подкатегория, город; поддержка сортировки в прямом/обратном порядке там, где это предусмотрено макетом. **[СОЗВОН]** Ещё «Пол автора» (Не имеет значения / Мужской / Женский); сортировка — «Сначала новые». **[МАКЕТ]**
- Активные фильтры отображаются плашками, которые можно снять. Все фильтры должны реально влиять на показываемые карточки. **[СОЗВОН]**
- Поиск и фильтры комбинируются логикой **AND**: поиск И режим И навыки И пол И город. **[ТЗ]** Внутри одного блока несколько отмеченных значений — «любой из» (два города через AND всегда дают пустой результат). **[РЕШЕНИЕ]**
- В исходном ТЗ: инпут поиска, select категории, radio «Учу / Учусь / Все». В макете и у наставника — дерево категорий с чекбоксами и «Всё / Хочу научиться / Могу научить»; делаем по макету. **[РЕШЕНИЕ]**

## 6. Вход и регистрация

### 6.1. Вход
- **Отдельный маршрут**, а не модальное окно.
- Поля email и пароль; обязательная валидация.
- Вход возможен только при совпадении введённых данных с моковым пользователем.
- Кнопки Google/Apple — неработающие заглушки.
- «Закрыть» возвращает назад по истории навигации. **[СОЗВОН]**

### 6.2. Регистрация — шаг 1
- Email и пароль, валидация формата и обязательности; переход кнопкой «Далее». **[СОЗВОН]**

### 6.3. Регистрация — шаг 2
- Аватар, имя, дата рождения, пол, город.
- Список навыков, которым хочет научиться: множественный выбор подкатегорий с согласованной категорией.
- После добавления пары «категория + подкатегория» предложено формировать отдельную удаляемую плашку и очищать селекты для следующего выбора. Это рекомендация наставника по UI, а не единственный допустимый интерфейс. **[СОЗВОН]**
- В макете (1:1673, 1:1717) «Категория…» и «Подкатегория навыка, которому хотите научиться» — выпадающие списки с чекбоксами. Делаем как в макете, с правилом связи из 3.3. **[МАКЕТ + РЕШЕНИЕ]**
- «Город» — список с поиском по вводу (1:1629); «Пол» — Не указан / Мужской / Женский (1:1585). **[МАКЕТ]**
- Дату выбрать с помощью стороннего компонента DatePicker, стилизованного под проект: выбор месяца и года, «Отменить» / «Выбрать» (1:1541).
- Аватар предпочтительно загружать файлом (проверять формат и размер); упрощённый ввод URL разрешён как альтернативный вариант. **[СОЗВОН]**

### 6.4. Регистрация — шаг 3
- Произвольное название **одного** навыка, которому пользователь может научить, согласованные категория и подкатегория, описание, фотографии.
- После заполнения открывается **превью** предложения с каруселью и описанием: «Ваше предложение. Пожалуйста, проверьте и подтвердите правильность данных» (1:1799). **[МАКЕТ]**
- «Редактировать» возвращает на форму; «Готово» завершает регистрацию, показывает подтверждение и переводит в авторизованное состояние. **[СОЗВОН]**

### 6.5. Маршрутизация регистрации
- Наставник рекомендовал три отдельных маршрута (`step-1`, `step-2`, `step-3`).
- При прямом переходе на шаг 2/3 без прохождения предыдущих шагов приложение перенаправляет на первый шаг. **[СОЗВОН]**

### 6.6. Куда пользователь попадает после регистрации
- После «Готово» пользователь авторизован и всегда попадает в **каталог**, его карточка появляется в ленте. **[ТЗ-Н]**
- Каталог открывается с окном «Ваше предложение создано» (1:2950), после «Готово» — каталог с шапкой вошедшего (1:2904). **[МАКЕТ]**
- Путь из макета «Предложить обмен → регистрация → обратно на страницу навыка» (1:3052) не делаем: гость идёт на вход (раздел 2). **[ТЗ-Н]**

## 7. Карточка и детальная страница навыка

### 7.1. Краткая карточка
- Данные владельца: имя, аватар, город, возраст, навыки по макету; лайки/избранное; ссылка/действие «Подробнее».
- «Хочет научиться» — до 2 тегов, остальные сворачиваются в «+N». **[ТЗ-Н]**
- Показ различных карточек одной и той же сущности должен быть согласован между главной, каталогом и избранным. **[СОЗВОН]**

### 7.2. Детальная карточка
- Отдельный прямой маршрут для конкретного предложения (в устаревшем ТЗ упоминался маршрут формата `skill/:id`; окончательный URL фиксирует команда).
- Название, описание навыка, карусель фотографий, пользовательский блок, «О себе» (только если пользователь заполнил в личном кабинете).
- Блок «Похожие предложения» — подбор по **той же подкатегории**, например «Музыка и звук».
- Лайк работает аналогично краткой карточке.
- Кнопки «Поделиться» и меню «…» — заглушки. **[СОЗВОН]**

### 7.3. Предложение обмена
- «Предложить обмен» меняет своё состояние, показывает подтверждение и создаёт уведомление **для инициатора**, что он предложил обмен указанному пользователю.
- Подтверждение — окно «Вы предложили обмен. Теперь дождитесь подтверждения. Вам придёт уведомление» + «Готово» (1:1977); после него кнопка — неактивная «🕓 Обмен предложен», на колокольчике — красная точка (1:1919). **[МАКЕТ]**
- Дополнительно появляется toast «Вы предложили обмен …». **[ТЗ-Н]**
- Гость — на вход с возвратом на страницу навыка (раздел 2). **[ТЗ-Н]**
- Реальное принятие/отклонение предложения вторым человеком, переписка и синхронизация пользователей не требуются. **[СОЗВОН]**

## 8. Уведомления

- Открываются из колокольчика в Header.
- Два раздела: **новые** и **просмотренные**.
- Уведомление содержит факт предложения обмена и действие «Перейти» к детальной карточке адресата.
- «Прочитать всё» переводит записи в просмотренные, после чего они не кликабельны. В транскрипции «просчитать всё» — вероятная ASR-ошибка. **[СОЗВОН]**
- Взаимодействия между реальными пользователями не реализуются. **[СОЗВОН]**
- Кнопка «Очистить» удаляет все уведомления; о новом уведомлении сообщает toast. **[ТЗ-Н]**
- Уведомления «Николай **принял** ваш обмен» из макета (1:2148, 1:2328) не делаем — обмены номинальные. **[ТЗ-Н]**

## 9. Избранное

- Доступно только авторизованным пользователям из иконки сердца в Header.
- Отдельный маршрут избранного (на созвоне произносится `favorites`).
- Список строится по сохранённым у текущего пользователя ID карточек/пользователей, которым он поставил лайк.
- На странице работают фильтры; при большом количестве карточек нужна **пагинация** — в понимании наставника это догрузка по 6 карточек при прокрутке, как в «Рекомендуемом». **[СОЗВОН]**
- Нажатие лайка и снятие лайка должны согласованно менять внешний вид карточки и состав избранного. **[СОЗВОН]**
- Избранное сохраняется после перезагрузки; при пустом списке — кнопка «Вернуться в каталог». **[ТЗ-Н]**

## 10. Личный кабинет

- Вход в меню по клику на аватар/имя; действия «Личный кабинет», «Выйти».
- **Рабочий раздел только «Личные данные»**: email, пароль, имя, дата рождения, пол, город, описание «О себе», аватар.
- «О себе» при регистрации не заполняется, первоначально пустое; только после редактирования в профиле отображается на детальной странице.
- «Изменить пароль» раскрывает дополнительное поле.
- Сохранённые изменения сразу видны в шапке (имя, аватар); гость при переходе в профиль попадает на вход. **[ТЗ-Н]**
- Разделы «Мои навыки», «Избранное» **внутри личного кабинета**, «Мои обмены», «Заявки» — заглушки. **[СОЗВОН]**
- При этом **отдельная полноценная страница избранного из Header обязательна** (раздел 9). Это не противоречие. **[СОЗВОН]**

## 11. Статические и технические страницы

- **«О проекте»:** отдельная страница с участниками конкретной команды и по желанию сведениями/ссылками GitHub. Наставник описал это как командную традицию. **[СОЗВОН]**
- **«Все навыки»:** в Header — выпадающее статическое меню категорий/подкатегорий, в Footer — переход к отдельной статической странице. Пункты этой страницы согласно созвону не обязаны быть кликабельными. **[СОЗВОН]**
- **404:** отображается для неизвестных маршрутов, есть кнопка возврата на главную; «Сообщить об ошибке» — заглушка.
- **500:** отдельный экран ошибки с аналогичным поведением; создать, хотя без backend такая ошибка естественным образом не возникает. **[СОЗВОН]** В ТЗ наставника от 31.10 не упомянута — оставляем как сказано на созвоне. **[РЕШЕНИЕ]**
- Footer: «Контакты», «Блог», «Политика конфиденциальности», «Пользовательское соглашение» — заглушки. **[СОЗВОН]**

## 12. Общие UI-компоненты и архитектура

- Командой выбрана **Feature-Sliced Design**. Рекомендуемое функциональное деление: `app`, `pages`, `widgets`, `features`, `entities`, `shared`; правила импортов между слоями и публичные `index.ts` фиксируются командной документацией. **[КОМАНДА]**
- При формировании задачи сначала выделять переиспользуемые элементы (кнопка, аватар, лайк, бейдж, блок пользователя), затем составные карточки, виджеты и целые страницы. **[СОЗВОН]**
- **Storybook:** наставник настойчиво рекомендовал, но не требовал для зачёта. Команда на предыдущем обсуждении решила его использовать, поэтому в текущем плане это **командная договорённость**, а не критерий наставника. **[СОЗВОН + КОМАНДА]**

## 13. Проверяемые сценарии приёмки

Ниже — редакторское представление явных требований созвона в виде проверок. Формулировки тестов не являются дословными цитатами.

1. Гость открывает главную, видит три секции и карточки в сетке по три колонки.
2. «Популярное» отсортировано по лайкам; «Новое» — по дате. Каждая секция переключается между 3 и 9 карточками.
3. «Рекомендуемое» догружает карточки при прокрутке порциями ориентировочно по шесть, не показывает всю коллекцию сразу.
4. Поиск запускается по Enter/лупе; фильтры реально ограничивают выборку; активные фильтры можно удалять.
5. Гость при попытке лайкнуть попадает в сценарий авторизации.
6. Авторизация принимает валидные моковые учётные данные, отклоняет неподходящие.
7. Регистрация проходит три шага; прямой вход на шаг 2/3 без предшествующего состояния направляет на шаг 1.
8. Выбор категории ограничивает подкатегории; выбор подкатегории способен автоматически выбрать категорию.
9. На шаге 2 можно выбрать несколько навыков «хочу научиться»; на шаге 3 создаётся ровно одно предложение «могу научить».
10. После подтверждения превью регистрация завершается и пользователь входит в систему.
11. Детальная страница показывает описание, фотокарусель, информацию о владельце и похожие предложения из его подкатегории.
12. «Предложить обмен» создаёт уведомление у инициатора; уведомление ведёт на карточку адресата и переводится в просмотренные.
13. Лайки отражаются в личном списке избранного; избранное имеет фильтры и догрузку при прокрутке.
13а. Гость со страницы навыка нажимает «Предложить обмен» → вход → возвращается на ту же страницу. После регистрации пользователь попадает в каталог и видит свою карточку. **[ТЗ-Н]**
13б. После «Предложить обмен» появляются toast и уведомление; «Очистить» удаляет уведомления; всё сохраняется после перезагрузки. **[ТЗ-Н]**
14. Личный кабинет позволяет редактировать данные; «О себе» появляется в карточке только после сохранения.
15. Страницы 404 и 500 существуют; кнопка «На главную» работает.
16. Заглушки остаются заглушками, где это явно оговорено; реализация backend, Google/Apple-login и мобильной версии не обязательна.

## 14. Командный процесс

### 14.1. Ответственность

- Тимлид и помощник (помощник дублирует обязанности тимлида **[ТЗ-Н]**): формируют задачи и зависимости, поддерживают очередь `Todo`, проверяют работоспособность решений в PR и принимают результаты. Наставник оставляет за собой более глубокую оценку качества кода. **[СОЗВОН]**
- Разработчик: выбирает **одну** задачу за раз, назначает себя исполнителем, переносит в работу, создаёт отдельную ветку, выполняет, открывает PR, исправляет замечания. Общей обязательной нормы количества задач на человека не озвучено. **[СОЗВОН]**
- Регулярное общение, командные созвоны хотя бы раз в неделю, обсуждение фундаментальных решений коллективно. Отдельные встречи с наставником — еженедельно. **[СОЗВОН]**

### 14.2. Git и Pull Request

- Ветки `main` и `develop`; `main` не используется для ежедневной разработки. Напрямую в общие ветки разработчики не коммитят. Каждая задача — отдельная ветка и отдельный PR в `develop`. **[СОЗВОН + КОМАНДА]**
- Коммитить только файлы, над которыми действительно велась работа; избегать слепого `git add .`. **[СОЗВОН]**
- Обновления зависимостей и существенные изменения конфигурации централизует тимлид после обсуждения с командой. **[СОЗВОН]**
- Conventional Commits, шаблон PR, ID задачи в названии, проверки `lint`, TypeScript, тестов и сборки **локально** (CI не развиваем; `ci.yml` из шаблона оставлен как есть), красные проверки — PR не мержится — командные правила. **[КОМАНДА]**
- Ориентир около 200 строк в коммите/PR наставник назвал **рекомендацией хорошего тона, а не строгим лимитом**. В `git-workflow.md` указан ориентир ~200 строк изменений в PR. При применении учитывать характер задачи, не считать это учебным блокирующим критерием без отдельного командного решения. **[СОЗВОН + КОМАНДА]**

### 14.3. Доска задач и переходы

**По созвону** требуются шесть столбцов: `Backlog` → `Todo` → `In progress` → `Review` → `Need Fix` → `Done`. `Backlog` управляется тимлидом и помощником; в `Todo` попадают готовые задачи без незакрытых блокеров. При замечаниях задача идёт `Review → Need Fix → In progress → Review`; при принятии — `Review → Done`. **[СОЗВОН]**

Командная документация (`docs/tasks/README.md`) приведена к этой схеме из шести колонок. **[КОМАНДА]**

Оформление задачи: создать **GitHub Issue, а не draft item**, сформулировать результат, приложить фрагмент Figma, критерии завершения, зависимости от подготовительных компонентов. **[СОЗВОН]**

### 14.4. Планирование

- План наставника по неделям: 1 — знакомство и нарезка задач, 2 — вёрстка, 3 — логика, 4 — правки; сроки могут смещаться, главное — общий темп. **[ТЗ-Н]** Соответствие фазам: неделя 1 — фазы 0–1, неделя 2 — фазы 2–3, неделя 3 — фазы 4–7, неделя 4 — фаза 8. **[КОМАНДА]**
- Командный roadmap (`docs/tasks/roadmap.md`) — только фазы, без привязки к датам: 0 фундамент ✅, 1 подготовка, 2 UI-кит, 3 вёрстка блоков и страниц, 4 данные и вход, 5 каталог и избранное, 6 регистрация, 7 навык, обмен, профиль, 8 финиш, 9 доп. фичи (по желанию). **[КОМАНДА]**
- Фазы 2–3 — вёрстка, 4–7 — логика, как советует наставник. Число задач — внутренний план команды, а не обязательный список наставника. **[КОМАНДА]**
- Старт с лёгких задач, затем средние, затем сложные — подход команды. **[КОМАНДА]**

## 17. Что необходимо подготовить перед реализацией

1. Утвердить карту маршрутов, наименование доменных сущностей и минимальную структуру моковых данных.
2. Зафиксировать обязательный MVP с учётом явных исключений наставника (заглушки, мобильная версия, тёмная тема, backend).
3. Согласовать изменения командного roadmap, чтобы дополнительные задачи не вытесняли основной функционал.
4. Довести канбан до шести статусов и связать задачи с зависимостями.
5. Утвердить описание общих UI-компонентов и правила FSD/public API.
6. Запускать работу по независимым задачам, соблюдая один исполнитель — одна активная задача, отдельные ветку и PR.
