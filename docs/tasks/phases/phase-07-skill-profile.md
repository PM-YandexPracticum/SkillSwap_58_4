# Фаза 7 — Навык, обмен, уведомления, профиль (логика)

**Цель:** работает путь «Подробнее → Предложить обмен → уведомление» и сохраняются «Личные данные».
**После фазы:** все обязательные функции MVP на месте.

## Архитектурная роль фазы

- **Отвечает за:** страницу навыка, похожие предложения, предложение обмена, уведомления и сохранение личных данных.
- **Подключает:** API и store фазы 4, сессию, готовые карточки и секции, toast, панель уведомлений и формы профиля.
- **Использует:** селекторы каталога и пользователя; пользовательские действия проходят через API сущностей и обновляют store.
- **Не дублирует:** загрузку данных, фильтрацию каталога, правила регистрации и собственные хранилища для обменов или уведомлений.
- **Результат для следующих фаз:** завершённые пользовательские сценарии, которые можно проверять сквозь приложение целиком.

### P7-03 · «Предложить обмен» ✅ 🔴
> **Что нужно сделать:** оживить кнопку «Предложить обмен». Гостя она ведёт на вход, а после него — обратно на эту страницу.
> Для вошедшего — создаём обмен и уведомление «Вы предложили обмен Ивану», показываем toast с тем же текстом и окно «Вы предложили обмен.
> Теперь дождитесь подтверждения. Вам придёт уведомление». После «Готово» кнопка становится неактивной «🕓 Обмен предложен»,
> на колокольчике — красная точка. Второй раз тому же человеку предложить нельзя.

- **Готовые зависимости:** `fetchExchanges` / `addExchange` / `selectHasProposed` из `@/entities/exchange`, `fetchNotifications` / `addNotification` из `@/entities/notification`, P7-01 и P4-08. Владелец уведомления — текущий пользователь, который предложил обмен. Сценарий использует существующую сессию; реальный вход реализован в P4-09.
- **Результат:** гостевой переход сохраняет исходный адрес для возврата после входа в P4-09; авторизованный пользователь создаёт обмен и уведомление без дублей, получает toast и окно подтверждения. После частичного сбоя повтор восстанавливает недостающую запись, а состояние сохраняется после перезагрузки. Бейдж карточки читает общий store; колокольчик подключается отдельно в P7-05.
- **Сессия:** сценарий читает `selectSession` из `@/entities/session`; `selectCurrentUser` не требуется для создания обмена. Гость переходит на вход с `state.from`; успешный вход и возврат реализует P4-09.
- **Сохранение и повтор:** `useProposeExchange` управляет кнопкой и окном, `persistExchangeProposal` координирует API сущностей. `notificationPending` сохраняет возможность восстановить уведомление после перезагрузки, `ensureExchangeNotification` создаёт его без дублей. Устаревшие ответы после смены навыка или сессии не открывают окно. Колокольчик и действия панели остаются в P7-05.
- **Файлы:** `src/features/exchange-propose/`, `src/pages/skill/ui/SkillPage.tsx` + тесты на логику и интеграцию

### P7-05 · Уведомления в действии ✅ 🟡
> **Что нужно сделать:** подключить уведомления: колокольчик показывает уведомления текущего пользователя; красная точка — пока есть новые.
> «Перейти» открывает страницу навыка того, кому предложили обмен. «Прочитать все» переносит новые в «Просмотренные»,
> где они больше не кликаются. «Очистить» удаляет все уведомления. Больше уведомления ничего не делают — обмены номинальные.

- **Уже готово:** `NotificationsPanel`, `NotificationItem` и `MarkAllReadButton` из P3-15 принимают данные и обработчики через пропсы; открытие окна управляется снаружи через `Dropdown` с `align="end"`. Имя в нужном падеже передаёт вызывающий код.
- **Готовая зависимость P4-07:** `fetchNotifications`, `selectNotifications`, `selectHasUnread`, `markAllRead()` и `clearAllNotifications()` из `@/entities/notification`; чтение и очистка сами берут владельца из сессии. В P4-07 панель к Redux не подключается.
- **Готовая интеграция:** шапка вошедшего пользователя принята в P5-09 (PR #207); текущего пользователя определяет `selectCurrentUser` из P4-09. Панель подключаем через существующий слот Header в MainLayout.
- **Контракт подключения:** Header уже содержит Dropdown и слот `notifications`; панель передаёт MainLayout, без импорта виджета в другой виджет и без второго колокольчика. `NotificationsPanel.onGo` передаёт id уведомления, а не id навыка: адрес навыка определяем по обмену и данным автора. Список и точку берём из селекторов текущей сессии, при выходе или смене пользователя чужие уведомления не показываем. Загрузка уведомлений не входит в DataProvider; её, состояния ошибок и результат чтения/очистки подключаем здесь. Проверяем сохранение после перезагрузки и отсутствие ложного успеха при ошибке записи.
- **Файлы:** `src/widgets/notifications-panel/`, `src/features/notifications-read/`, `src/widgets/header/`, `src/app/layouts/MainLayout.tsx`
- **Результат интеграции:** загрузчик уведомлений перенесён в `useNotifications`, который запускается независимо от открытия панели. `Header` получает точку через `selectHasUnread`, а `MainLayout` передаёт панели данные и действия через слот. Ошибка первоначальной загрузки показывает понятное сообщение и ручную кнопку «Повторить»; пустое состояние появляется только после успешной загрузки. Ошибки «Прочитать все» и «Очистить» не скрывают сохранённый список и не показывают ложный успех.
- **Надёжность:** `updateMany` и `removeMany` выполняют пакетные операции через общую очередь mock DB; учитываются владельцы, новые записи, переполнение хранилища, смена сессии, StrictMode и частично сохранённый обмен. `onGo` разрешает маршрут только к навыку адресата. Иконка панели сверена с Figma.

### P7-06 · «Личные данные»: сохранение ✅ 🔴

> «Изменить пароль» открывает дополнительное поле нового пароля (не окно). «Сохранить» активна, только когда что-то изменили
> и всё верно; данные сохраняются в «базе», новые имя и аватар сразу видны в шапке, заполненное «О себе» появляется на странице навыка.

Подключаем эту схему к форме; обязательность нового пароля задаём только при его изменении, используя общий `passwordField` и `PasswordInput` из P2-06. Обновление имени, фото и «О себе» должно приходить потребителям из общего store.
