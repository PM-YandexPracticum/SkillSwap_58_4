### P7-03 · «Предложить обмен» 🔴
> **Что нужно сделать:** оживить кнопку «Предложить обмен». Гостя она ведёт на вход, а после него — обратно на эту страницу.
> Для вошедшего — создаём обмен и уведомление «Вы предложили обмен Ивану», показываем toast с тем же текстом и окно «Вы предложили обмен.
> Теперь дождитесь подтверждения. Вам придёт уведомление». После «Готово» кнопка становится неактивной «🕓 Обмен предложен»,
> на колокольчике — красная точка. Второй раз тому же человеку предложить нельзя.

- **Готовая зависимость P4-07:** `fetchExchanges` / `addExchange` / `selectHasProposed` из `@/entities/exchange`, `fetchNotifications` / `addNotification` из `@/entities/notification`. Владелец уведомления — текущий пользователь, который предложил обмен; текст, toast и окно собирает эта задача. P7-01 уже влита, для интеграции остаётся P4-09; задача находится в Todo.
- **Готовая зависимость P4-08:** закрытые маршруты защищены, исходный адрес сохраняется в `state.from`. Для интеграции P7-03 остаётся P4-09; P7-01 уже готова.
- **После зависимостей:** кто предлагает обмен — `selectCurrentUser` из `@/entities/user` (P4-09), гость — `null`.
- **Что заменяем:** `SkillPage` сейчас хранит демонстрационный `isProposed` локально. Вместо него подключаем `selectHasProposed` и готовую загрузку обменов при прямом открытии страницы навыка: DataProvider загружает только пользователей, навыки, категории и города. Кнопку и `ExchangeProposedModal` повторно не верстаем. После записи обмена и уведомления показываем успех, ошибки и повтор после частичного сбоя проверяем отдельно — без второго обмена тому же человеку. В каталоге бейдж уже работает через тот же store; сам колокольчик подключает P7-05.

### P7-05 · Уведомления в действии 🟡
> **Что нужно сделать:** подключить уведомления: колокольчик показывает уведомления текущего пользователя; красная точка — пока есть новые.
> «Перейти» открывает страницу навыка того, кому предложили обмен. «Прочитать все» переносит новые в «Просмотренные»,
> где они больше не кликаются. «Очистить» удаляет все уведомления. Больше уведомления ничего не делают — обмены номинальные.

- **Уже готово:** `NotificationsPanel`, `NotificationItem` и `MarkAllReadButton` из P3-15 принимают данные и обработчики через пропсы; открытие окна управляется снаружи через `Dropdown` с `align="end"`. Имя в нужном падеже передаёт вызывающий код.
- **Готовая зависимость P4-07:** `fetchNotifications`, `selectNotifications`, `selectHasUnread`, `markAllRead()` и `clearAllNotifications()` из `@/entities/notification`; чтение и очистка сами берут владельца из сессии. В P4-07 панель к Redux не подключается.
- **Остаётся дождаться:** шапки вошедшего пользователя (P5-09); текущего пользователя определяет `selectCurrentUser` из P4-09. Подключение панели не начинается автоматически после её вёрстки.
- **Контракт подключения:** Header уже содержит Dropdown и слот `notifications`; панель передаёт MainLayout, без импорта виджета в другой виджет и без второго колокольчика. `NotificationsPanel.onGo` передаёт id уведомления, а не id навыка: адрес навыка определяем по обмену и данным автора. Список и точку берём из селекторов текущей сессии, при выходе или смене пользователя чужие уведомления не показываем. Загрузка уведомлений не входит в DataProvider; её, состояния ошибок и результат чтения/очистки подключаем здесь. Проверяем сохранение после перезагрузки и отсутствие ложного успеха при ошибке записи.

### P7-06 · «Личные данные»: сохранение 🔴
> **Что нужно сделать:** сделать сохранение «Личных данных»: поля заполнены данными пользователя; можно поменять почту, имя, дату, пол, город, «О себе» и фото.
> «Изменить пароль» открывает дополнительное поле нового пароля (не окно). «Сохранить» активна, только когда что-то изменили
> и всё верно; данные сохраняются в «базе», новые имя и аватар сразу видны в шапке, заполненное «О себе» появляется на странице навыка.

- **Уже готово:** `createProfileSchema(cityIds)` из `profile-edit/model/schema.ts` уже использует общие правила email, имени, возраста, города и «О себе», допускает `gender: null`. Подключаем эту схему к форме; обязательность нового пароля задаём только при его изменении, используя общий `passwordField` и `PasswordInput` из P2-06. Текущего пользователя предоставит `selectCurrentUser` (P4-09); фото — общий AvatarUpload после P6-04 и утилиты P2-14.
- **Что заменяем:** демонстрационные значения и локальные состояния ProfileForm — данными текущего пользователя и единой формой. После успешной записи через P4-06 обновляем исходные значения формы; при ошибке введённое сохраняется. Проверку уникальности изменённого email согласуем с P4-06, исключая самого пользователя. Дату вводим готовым DatePicker; аватар не загружаем второй независимой реализацией. Обновление имени, фото и «О себе» должно приходить потребителям из общего store.
