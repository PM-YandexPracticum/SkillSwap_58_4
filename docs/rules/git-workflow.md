# Git-процесс

## Ветки

```
main        ← только стабильный код, напрямую не трогаем
└── develop ← основная ветка разработки, PR только сюда
    └── feature/catalog-filters   ← твоя задача
```

Префиксы веток: `feature/`, `fix/`, `refactor/`, `docs/`, `chore/`, `test/`.
Имя — `kebab-case`, начинается с ID задачи из [плана](../tasks/roadmap.md): `feature/p2-02-buttons`, `fix/p4-03-search-reset`.

## Перед началом задачи

```bash
git checkout develop
git pull
git checkout -b feature/название-задачи
```

## Коммиты

По [Conventional Commits](https://www.conventionalcommits.org/ru/): `<тип>: <что сделано>`.
После P1-14 удобнее коммитить командой `npm run commit` — она сама спросит тип и описание.

| Тип | Когда |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление бага |
| `refactor` | переделка без изменения поведения |
| `style` | стили и форматирование |
| `test` | тесты |
| `docs` | документация и README |
| `chore` | конфиги, зависимости |

```
feat: добавить фильтр по городам
fix: исправить отображение карточки без аватара
```

Коммить часто и маленькими порциями — так проще ревьюить и откатывать.

## Что добавлять в коммит

- **Только файлы, над которыми работал.** Никогда `git add .` — добавляй по одному: `git add src/shared/ui/Button/`.
- Перед коммитом смотри `git status` и `git diff --staged`: нет ли чужих файлов, `package.json`, `package-lock.json`, случайно изменённых образцов в `src/shared/api/mock-db/seed/`.
- **`package.json` и зависимости меняет только тимлид, прямо в `develop`.** Нужна библиотека — пиши тимлиду, не ставь сам.
- PR, в котором «Files changed» — сотни файлов, не принимается.

## Pull request

- Из своей ветки **в `develop`**.
- Заголовок PR начинается с ID задачи: `[P2-02] Кнопки Button и IconButton`.
- В описании — `Closes #<номер issue>`, чтобы карточка на [канбан-доске](https://github.com/orgs/PM-YandexPracticum/projects/133/views/1) закрылась сама.
- Ориентир — около 200 строк изменений. Это правило хорошего тона, а не жёсткий лимит; 500+ строк — уже тяжело читать, дели задачу.
- **Одна задача = одна ветка = один PR.** Брать можно только одну задачу за раз — следующую после того, как сдал текущую.
- Заполни шаблон PR (`.github/pull_request_template.md`), приложи скриншот, если менялся UI.
- **CI нет** — проверки только локальные. Перед PR: `npm run lint`, `npx tsc --noEmit`, `npm run test`, `npm run build`
  (после P1-14 это делает хук pre-push через `npm run verify`).
- Ревьюер при сомнениях сам запускает проверки в ветке PR. Красные проверки — PR не мержится.
- Файл `.github/workflows/ci.yml` из стартового шаблона оставлен как есть: GitHub может показывать его проверки в PR, но мы его не развиваем и на него не опираемся.

## Ревью

- Вливает только тимлид или помощник тимлида.
- Тимлид делает `git pull`, переключается на ветку PR, запускает проект и проверяет, что всё **работает как описано в задаче** и похоже на макет.
  За качество кода отвечает наставник — тимлид проверяет работоспособность.
- Есть замечания — пишем в PR, карточку переносим в **Need fix**. Разработчик правит новым коммитом в ту же ветку и возвращает карточку в **Review**.
- Всё хорошо — мерж в `develop`, карточка в **Done**.

## Запрещено

- `git push --force` в общие ветки, `merge --no-ff` в `develop`.
- Коммитить напрямую в `main` и `develop`.
- Коммитить `.env.local`, `node_modules`, `dist`.
