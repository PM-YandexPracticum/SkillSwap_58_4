# Git-процесс

## Ветки

```
main        ← только стабильный код, напрямую не трогаем
└── develop ← основная ветка разработки, PR только сюда
    └── feature/catalog-filters   ← твоя задача
```

Префиксы веток: `feature/`, `fix/`, `refactor/`, `docs/`, `chore/`, `test/`.
Имя — `kebab-case`, начинается с ID задачи из [плана](../tasks/roadmap.md): `feature/p2-02-buttons`, `fix/p4-03-search-reset`.

## Перед началом задачи

```bash
git checkout develop
git pull
git checkout -b feature/название-задачи
```

## Коммиты

По [Conventional Commits](https://www.conventionalcommits.org/ru/): `<тип>: <что сделано>`.
После P1-14 удобнее коммитить командой `npm run commit` — она сама спросит тип и описание.

| Тип | Когда |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление бага |
| `refactor` | переделка без изменения поведения |
| `style` | стили и форматирование |
| `test` | тесты |
| `docs` | документация и README |
| `chore` | конфиги, зависимости |

```
feat: добавить фильтр по городам
fix: исправить отображение карточки без аватара
```

Коммить часто и маленькими порциями — так проще ревьюить и откатывать.

## Что добавлять в коммит

- **Только файлы, над которыми работал.** Никогда `git add .` — добавляй по одному: `git add src/shared/ui/Button/`.
- Перед коммитом смотри `git status` и `git diff --staged`: нет ли чужих файлов, `package.json`, `package-lock.json`, случайно изменённых образцов в `src/shared/api/mock-db/seed/`.
- **`package.json` и зависимости меняет только тимлид, прямо в `develop`.** Нужна библиотека — пиши тимлиду, не ставь сам.
- PR, в котором «Files changed» — сотни файлов, не принимается.

## Как создавать коммиты используя Commitizen

**Commitizen** - библиотека, которая упрощает и автоматизирует процесс создания коммита по [Conventional Commits](https://www.conventionalcommits.org/ru/) с использованием скриптов.

Если выбираете данный способ, чтобы закоммитить изменения, то нужно проделать следующие действия:
- **Шаг 1. Проиндексировать изменения** - добавить изменения в staged (команда `git add <имя_файла>`), без этого процесс создания коммита не запустится;
- **Шаг 2. Введите в терминале команду `npm run commit`** - данная команда запускает интерактивный мастер по созданию коммита;
- **Шаг 3. Заполните опросник**
  - **Шаг 3.1. Выбор типа изменений (Select the type of change)** - Нужно выбрать тип коммита из списка. При выборе ориентироваться на раздел "Коммиты" документации.
    - Основные варианты, на которые стоит ориентироваться:
      - `feat` — добавление новой функциональности (фичи);
      - `fix` — исправление ошибки (бага);
      - `refactor` — рефакторинг кода (изменение структуры без изменения поведения);
      - `docs` — изменения только в документации (например, правка .md файлов);
      - `style` — изменения, не влияющие на логику кода (пробелы, форматирование, точка с запятой);
      - `test` — добавление или исправление тестов;
      - `chore` — рутинные задачи, настройка сборки, обновление зависимостей (ставит только тимлид и помощник);
    - Системные типы:
      - `revert` — отменяет предыдущий коммит;
    - Остальные типы вряд ли пригодятся в работе, при желании можно посмотреть [документацию библиотеки](https://commitizen-tools.github.io/commitizen/);
  - **Шаг 3.2. Область изменений (What is the scope of this change)**
    - Здесь нужно указать, к какой части проекта относятся изменения (например, auth, header, api, button), либо файл, в котором проводились изменения.
    - Если не знаете, что написать, или изменение глобальное — просто нажмите Enter, чтобы пропустить этот шаг, тогда название коммита примет такой вид (информация в скобках не появится): `<тип_изменений>: <описание>`.
  - **Шаг 3.3. Краткое описание (Write a short, imperative tense description)**
    - Напишите кратко суть изменения.
    - Справа будет отображаться счетчик символов (максимум ~93). Нажмите Enter.
  - **Шаг 3.4. Подробное описание (Provide a longer description)**
    - Опишите подробности изменения, если это необходимо. Если коммит простой — просто нажмите Enter, чтобы пропустить.
  - **Шаг 3.5. Критические изменения (Are there any breaking changes?)**
    - Если ваши изменения ломают обратную совместимость (обычно это касается библиотек или API), выберите y (yes) и опишите, что именно сломалось.
    - Если не знаете, что писать, выберите n (no) и переходите к следующему шагу - в 99% случаях выбирается этот вариант.
  - **Шаг 3.6. Открытые issues (Does this change affect any open issues?)**
    - На этом шаге всегда выбираем n (no) - наш workflow на github не требует указывать данную информацию в коммите, поэтому можно смело пропускать этот шаг. Параметр n (no) особо не повлияет на удобство.
    - *Принцип работы: Ставится y (yes), если коммит закрывает какую-то задачу/баг в GitHub, при выборе y указывается номер issue (например, #12).*
- **Шаг 4. Автоматическая проверка (Husky)**
  - После того как вы ответите на все вопросы, Commitizen сформирует сообщение (например, `feat(auth): добавить страницу логина`) и запустит процесс коммита.
  - В этот момент сработает pre-commit хук (Husky). Он автоматически запустит линтер и форматтер (через lint-staged) для тех файлов, которые вы добавили в шаге 1.
    - Если проверки пройдены — коммит создастся.
    - Если есть ошибки — коммит остановится, нужно будет исправить ошибки и повторить попытку.
- **Шаг 5. Продолжение работы / Отправка изменений (Push)**
  - После успешного создания коммита можно дальше продолжать работу над задачей или делать push на удаленную ветку задачи и создавать pull request, если готовы отправить работу на ревью.

    ```
    git push -u origin <тип>/<название_задачи>
    ```





## Pull request

- Из своей ветки **в `develop`**.
- Заголовок PR начинается с ID задачи: `[P2-02] Кнопки Button и IconButton`.
- В описании — `Closes #<номер issue>`, чтобы карточка на [канбан-доске](https://github.com/orgs/PM-YandexPracticum/projects/133/views/1) закрылась сама.
- Ориентир — около 200 строк изменений. Это правило хорошего тона, а не жёсткий лимит; 500+ строк — уже тяжело читать, дели задачу.
- **Одна задача = одна ветка = один PR.** Брать можно только одну задачу за раз — следующую после того, как сдал текущую.
- Заполни шаблон PR (`.github/pull_request_template.md`), приложи скриншот, если менялся UI.
- **CI нет** — проверки только локальные. Перед PR: `npm run lint`, `npx tsc --noEmit`, `npm run test`, `npm run build`
  (после P1-14 это делает хук pre-push через `npm run verify`).
- Ревьюер при сомнениях сам запускает проверки в ветке PR. Красные проверки — PR не мержится.
- Файл `.github/workflows/ci.yml` из стартового шаблона оставлен как есть: GitHub может показывать его проверки в PR, но мы его не развиваем и на него не опираемся.

## Ревью

- Вливает только тимлид или помощник тимлида.
- Тимлид делает `git pull`, переключается на ветку PR, запускает проект и проверяет, что всё **работает как описано в задаче** и похоже на макет.
  За качество кода отвечает наставник — тимлид проверяет работоспособность.
- Есть замечания — пишем в PR, карточку переносим в **Need fix**. Разработчик правит новым коммитом в ту же ветку и возвращает карточку в **Review**.
- Всё хорошо — мерж в `develop`, карточка в **Done**.

## Запрещено

- `git push --force` в общие ветки, `merge --no-ff` в `develop`.
- Коммитить напрямую в `main` и `develop`.
- Коммитить `.env.local`, `node_modules`, `dist`.
